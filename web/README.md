# NES Emulator Web

[简体中文](./README.zh-CN.md) · **English**

A React + Vite front end driving the Rust/WASM NES core compiled from `crates/nes-wasm`.
Drop a `.nes` file anywhere on the page, or paste a ROM URL into the sidebar, and start
playing.

## Requirements

- Node.js 18+
- A Rust toolchain and [`wasm-pack`](https://drager.github.io/wasm-pack/) when recompiling
  the WASM core

## Commands

```bash
npm install         # install dependencies
npm run dev         # dev server at http://localhost:5173
npm run build       # typecheck + production build into dist/
npm run build:pages # sub-path build (GitHub Pages); base comes from PAGES_BASE, default /
npm run preview     # preview the production build locally
npm run typecheck   # typecheck only
npm run build:games # regenerate public/games.json (the game list)
npm run build:wasm  # regenerate the core bindings under src/wasm/ with wasm-pack
```

`src/wasm/` is generated by `npm run build:wasm` and is not under version control. The
first run of that command has `wasm-pack` download `wasm-bindgen` and friends, so it needs
network access.

Deployment to GitHub Pages is handled by `.github/workflows/deploy-pages.yml` in the
repository root: it regenerates `src/wasm/`, builds with `npm run build:pages` under the
`<repo>` sub-path, and publishes `dist/`. Both `games.json` and the AudioWorklet take their
paths from `import.meta.env.BASE_URL`, so a sub-path deployment needs no code changes. See
"Deployment (GitHub Pages)" in the root [`README.md`](../README.md).

## Interface

The UI is built from the Animal Crossing–style
[animal-island-ui](https://github.com/guokaigdg/animal-island-ui) components, with the
stylesheet imported once in `src/main.tsx` (`import 'animal-island-ui/style'`).
`src/styles.css` only handles this project's own layout: it does not override the library's
component colors, corner radii, or shadows, but reads the `--animal-*` tokens the library
declares on `:root`, keeping custom parts on the same palette as the components.

- Components used: `Card` / `Title` / `Button` / `Input` / `Switch` / `Tag` / `Modal` /
  `Skeleton` / `Collapse` / `Divider` / `Tooltip` / `Notification` / `Background` /
  `Cursor` / `Footer`.
- Icons all come from `naive-icons` (a runtime dependency of the library); no emoji and no
  hand-made SVG.
- Load failures go through the imperative `Notification` API, and the confirmation for
  "clear save" goes through `Modal`.

## Bundle size

The `trimIslandAssets` plugin in `vite.config.ts` removes two categories of declarations
this project doesn't use from the library's stylesheet, cutting `dist/` from about 4.6 MB
to about 730 KB:

- **Noto Sans SC's 6 `@font-face` blocks** (three Simplified Chinese faces at about 1.15 MB
  each, with no `unicode-range`, so the browser may download all of them). Every
  `font-family` list in the library is immediately followed by system fonts
  (`PingFang SC` / `Microsoft YaHei`), so dropping the faces only makes Chinese use the
  system font; the rest of the typography is unchanged. Latin text still uses Nunito (three
  Latin subsets, about 48 KB total).
- **4 decorative scene illustrations** (about 316 KB). They only serve
  `Background type="sweet-corner" | "coffee-break"` and the `Progress` `variant`, neither
  of which this project uses; if you use them later, delete the matching regex line from
  the plugin.

If the library changes its fonts or images, the plugin emits a build-time warning instead
of failing silently.

## Mobile page (/m)

The wide page squeezes nine panels into one column on a phone, which leaves the game
picture tiny, so the mobile version is two separate routes:

```
/                       the wide page (unchanged)
/m                      game-list dashboard: search, local ROM, pick one at random
/m/play?game=<name>     play page: picture on top, touch pad below, everything else in a top-right toolbar
```

- `?game=` is the **unique game name** in `games.json` (the list comes from a single flat
  catalog with no duplicate names), so sharing it in a chat still reads as a legible
  `/m/play?game=1943`. If the name isn't found in the list, the play page says so and
  offers a way back to the list.
- Visiting the site root with a user agent that is clearly a phone enters `/m`
  (`src/mobile/entry.ts`; the decision happens before the first frame renders, so the wide
  page never flashes, and the address is rewritten with `replaceState`, leaving no
  "go back and bounce forward again" history entry). Only platforms that are certainly
  phones match (`Android…Mobile` / `iPhone` / `iPod` / Windows Phone…), while tablet and
  desktop user agents keep the wide page. The UI has **no** desktop/mobile toggle: the
  redirect is recorded once per session in `sessionStorage`, so opening `/` again in the
  same tab (typing the address, an old bookmark) no longer redirects — that is the only way
  to reach the wide page from a phone, and it avoids being bounced back with nowhere to go.
- The play page is a `100dvh` grid: top bar, picture, and pad as three rows that don't
  scroll against each other; **pause, reset, mute, fullscreen, save slots, switch ROM, load
  from URL** all live in a `Drawer` opened from a top-right button (the drawer's background
  scrim depth is turned off in `vite.config.ts` — it scales the canvas along with
  everything else and makes the picture blurry). While paused, tapping the picture resumes.
- In landscape (`orientation: landscape` and height ≤ 540px) the pad moves to either side of
  the picture: the D-pad and SELECT hug the left, B/A and START hug the right, and the
  picture is centered, so the thumbs land where they already are when holding a phone. The
  pad container itself is `pointer-events: none`, and only buttons are tappable, so the
  middle of the picture still belongs to the picture (tapping it resumes after a pause).
- `viewport-fit=cover` hands the whole screen to the page, so every edge the system claims is
  given back with `env(safe-area-inset-*)`: the phone pages pad all four sides (holding a
  notched phone sideways puts the unsafe areas on the *left and right*, which is exactly where
  the pad sits), the sticky search box pins below the status bar instead of under it, the
  portalled tools drawer keeps its content off the right edge, and the wide-screen shell pads
  itself too. All insets fall back to 0, so devices without them are unaffected.
- Fullscreen requests the whole page rather than the picture: the drawer, dialogs, and
  notifications are attached to `body`, and element fullscreen would hide them.
- The touch pad is in `src/mobile/TouchPad.tsx`: one container handles pointer events for
  the whole panel and re-decides what is pressed from the coordinates on every move, so the
  D-pad is "one stick" rather than four separate buttons (a diagonal means two directions
  held at once, sliding a thumb onto another button switches immediately), multi-touch
  doesn't interfere with itself, `touch-action: none` keeps a slide from becoming a page
  scroll, and pressing gives slight haptic feedback.
- The direction area is therefore drawn as one continuous pad rather than four keys: the
  whole circle is the target (the element keeps 8 px of invisible margin around the face it
  paints, so a thumb reaching for a corner still gets its diagonal), the arrows are only
  printed hints, and the stick head leans the way the thumb pushes while the matching arrows
  light up. Nothing has to be aimed at; the direction comes from where the thumb landed.
  A/B/SELECT/START stay discrete buttons — the NES reads eight digital directions and has no
  analogue value to offer a real stick.
- A pointer belongs to the control it landed on, so a press is never dropped mid-game. On the
  stick the direction keeps coming from the coordinates — sliding well past the rim holds it,
  and only the dead zone or lifting the finger releases it — while a button press hands over
  to a neighbouring button (that is how B→A rolls work), keeps holding when the thumb drifts
  into the pad's empty space, and lets go once the finger leaves the pad.
- Presses buzz on the platforms that can: `src/mobile/haptics.ts` wraps `navigator.vibrate`
  (Android browsers; WebKit has never implemented it, so an iPhone stays silent and the switch
  is disabled there) with 12 ms for the face buttons and 6 ms once per stick push — rolling
  from one direction to the next does not buzz again. It starts on and can be turned off in
  the toolbar, under 「震动」 next to 「静音」.
- Row selection in the list listens for a **tap** rather than `click`
  (`src/mobile/useTap.ts`): when a list is still coasting (or has just stopped), WebKit uses
  the first tap to brake and dispatches no `click`, which turns into "you have to tap twice
  to enter a game". This recognizes a tap on `pointerup` (press-to-release displacement
  ≤ 10px; a scroll is interrupted by `pointercancel`) and prefers the `click` that arrives
  afterwards, with a fallback timer only for when the `click` really never comes — mutating
  the DOM directly inside `pointerup` would make that following `click` land on the newly
  appeared overlay and instantly close the toolbar drawer it just opened.
- The mobile page disables text selection and the long-press callout wholesale
  (`body.phone-ui`, attached to `body` by `src/App.tsx` per route, so portaled drawers and
  dialogs are covered too): rows, buttons, and the picture never drag out a selection
  magnifier or the iOS menu; **text inputs are the exception**, so the search box and the
  ROM URL field still allow selecting text and moving the caret. The wide page is unchanged.
- The picture may be scaled by non-integer multiples on the mobile page: on a phone, "1×
  crisp but a third of the screen" is worse than "fills the screen". The window itself is
  the picture's aspect-ratio box, taking the ratio from the frame size the core exports
  (`MobileStage` writes it as `aspect-ratio` from `screen`): in portrait it fills by width,
  and in landscape the width is derived from the available height and centered, so there are
  no letterbox bars and no stretched picture.
- Deep links (`/m/play?game=…`) have no server-side rewrite on GitHub Pages, so the build
  also emits a `404.html`: it stuffs the original address into `?route=` and hands it back
  to the app, and `router.ts` restores it with `history.replaceState` before the first
  frame renders, so refreshes and shared links open the right page directly.

## Loading a ROM

- **Local file**: drop it anywhere on the page, or use "select ROM" in the toolbar.
- **Game list**: "game list" in the toolbar opens a dialog where you can search by name and
  start playing; the running cartridge is marked as such.
- **URL**: paste a direct ROM link into "load from URL" in the sidebar and press Enter (a
  link without `http(s)://` is treated as `https`). A downloaded image goes through exactly
  the same iNES / mapper validation as a local file. GitHub `blob` (file page) and `raw`
  links are rewritten to the direct `raw.githubusercontent.com` URL — the 302 redirect from
  `github.com/…/raw/…` carries no `Access-Control-Allow-Origin`, so the browser discards
  that response. Links to other sites need the server to allow cross-origin requests (CORS).
- **Save ownership**: battery saves and save states are separated by "source" — the file
  name for a local file, the normalized URL for a link — so a local copy and a linked copy
  of the same ROM never overwrite each other.

### Game list data

`public/games.json` is a static file shaped like
`[{ "name": "90坦克", "url": "https://raw.githubusercontent.com/…" }]`, preloaded with the
932 ROMs from [mengfei523060/nesrom](https://github.com/mengfei523060/nesrom) (names and
direct links only, **no ROM data**; ROMs in the repository are never committed). The file
is requested only when the dialog is first opened, so it adds nothing to the initial load;
the list is sorted by name, renders 20 rows up front, and appends the next batch of 20 as
you scroll near the bottom (`IntersectionObserver` watching a sentinel at the end of the
list), so there is no pager and never a thousand rows rendered at once; the search box is
pinned to the top, so you can change the keyword deep in the list.

Switching to a different repository, or updating the list:

```bash
npm run build:games                      # default: the master branch of mengfei523060/nesrom
npm run build:games -- owner/repo main   # specify repository and branch
GITHUB_TOKEN=… npm run build:games       # raise the GitHub API quota (60/hour unauthenticated)
```

The script prefers the GitHub API and automatically falls back to walking the repository
pages when rate-limited (no quota limit).

## Controls

| Action | Keys |
| --- | --- |
| D-pad | `W` `A` `S` `D` |
| A | `J` / `I` |
| B | `K` / `O` |
| Start | `Enter` / `Space` |
| Select | `Shift` |
| Pause / resume | `P` |

On touch devices you can use the virtual pad on the right.

### About Select

The title screen of *Super Mario Bros.* only samples Select on **1 frame out of every 16**
(the game gates it with a `$0780` counter), and its controller-reading routine (`$8E5C`)
turns Select into a "just pressed" flag that is **valid for a single frame only**. So an
ordinary ~100 ms tap has only about a 1/16 chance of landing on the sampled frame, and
holding the button down doesn't work at all — the flag has already expired before the next
sampling window opens. The game also has a secondary gate (`$07A2`) that periodically masks
Select off, so even perfect timing can be discarded.

This is the ROM's own logic (pinned in `crates/nes-wasm` by the
`smb_select_is_sampled_once_per_sixteen_frames` test), not a defect in the emulator or the
front end. **This project deliberately does no turbo/retry handling**: a button is reported
to the controller exactly as pressed, preserving the timing of the original hardware. The
cost is that switching P1 / P2 takes several presses just like on real hardware (or a quick
tap on the right frame). If input assistance is ever wanted, it only takes a pulse wrapper
around `setButton` in `src/emulator/NesEmulator.ts`; neither the core nor the rendering
changes.

## Implementation notes

- **Frame clock**: frames advance at the NES's 60.0988 Hz rather than the screen refresh
  rate, accumulating time slices with `requestAnimationFrame` and capping how many frames
  can be caught up in one go; a backlog is dropped when a tab becomes visible again, to
  avoid fast-forwarding.
- **Integer scaling**: the canvas back buffer is fixed at 256×240; a `ResizeObserver`
  computes the integer scale factor and only the CSS size changes, which together with
  `image-rendering: pixelated` yields sharp pixels.
- **Audio**: the core produces a batch of interleaved stereo samples per emulated frame,
  handed to an AudioWorklet queue that plays them at the sound card's pace; browsers
  without AudioWorklet fall back to `ScriptProcessorNode`.
- **ROM validation**: whether a local file or a downloaded URL, the iNES header and mapper
  support are checked before anything reaches the core, producing readable errors; a failed
  load keeps the game currently running.
- **Battery saves**: a cartridge with a battery writes its save to `localStorage` under the
  ROM file name and restores it automatically when the same ROM is dropped in again; "clear
  save" in the toolbar deletes that save and resets the cartridge after a confirmation,
  handy for starting over.
- **Game list**: `scripts/build-game-list.mjs` generates the static `public/games.json`, and
  the front end fetches it only when the dialog opens and filters by name, keeping close to
  a thousand entries out of the initial bundle.
- **Save states**: `save_state` / `load_state` encode the mutable state of the CPU, PPU,
  APU, bus, and the cartridge (bank selection, IRQ counters, work RAM, expansion audio…) as
  a byte stream, with PRG-ROM not stored again; the sidebar offers 4 slots in IndexedDB,
  which can be saved to, loaded from, or cleared at any time.
